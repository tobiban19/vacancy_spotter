# Vacancy Spotter: аудит архитектуры и логирования

Дата: 14 октября 2026, Europe/Moscow. Рабочая папка: `D:\Vacancy spotter`.
Аудируемая версия: `7480094e4cbcf3c15e801c2a69a78c944eaa1f80`, ветка `codex/preserve-local-2026-10-14`.

## Решение

Продолжать проект на существующем стеке, но перед запуском провести адресный рефакторинг бэкенда. Полное переписывание не обосновано. Текущая версия не готова к платному публичному запуску.

FastAPI, aiogram, Telethon, React/TypeScript и разделение на API, DTO, репозиторий и генерацию откликов подходят задаче. Проверки владельца в CRUD карточек и портфолио уже есть, HMAC сравнивается через `compare_digest`, карточки и ожидание перегенерации сохраняются в SQLite. Основные проблемы находятся на границах операций: авторизация, транзакции, повторные запросы, доставка сообщений, запуск и деплой.

SQLite можно сохранить для небольшого сервиса на одном сервере с одним набором воркеров, явными транзакциями и резервным копированием. При нескольких репликах и независимых воркерах стоит перейти на PostgreSQL. Переход БД сам по себе не исправит перечисленные ошибки.

## Приоритетные проблемы

### P0. Текущий токен бота доступен в публичной истории Git

В старых blob-версиях `backend/database.py`, достижимых из `origin/main`, найдены два разных значения формата полного Telegram bot token. Одно побайтно совпало с текущим локальным `BOT_TOKEN`. Репозиторий публичный. Сами значения не выводились и в этот отчёт не включены. Действительность токена через Telegram API не проверялась.

**До любого запуска:** отозвать токен через BotFather, выдать новый и обновить локальные/серверные настройки. Удаление строки из текущего кода не устраняет раскрытие. Очистку истории при необходимости делать отдельной согласованной операцией; считать старый токен раскрытым независимо от неё. Не коммитить новый ключ.

### P1. Одобрение подписок не проверяет администратора и не защищено от повторов

Источник: [bot_service.py:583–598](../../backend/bot_service.py#L583), [629–640](../../backend/bot_service.py#L629).

Обработчики `admin_approve` / `admin_reject` не вызывают `_is_admin`. Одобрение содержит только ID пользователя и число дней; сохранённого запроса оплаты и перехода состояния решения нет.

**Проверено изолированно:** вызов обработчика с неадминистратором продлил подписку; повтор того же callback добавил ещё семь дней. Это доказывает поведение обработчика, но не доказывает, что произвольный пользователь сейчас имеет доступ к административной клавиатуре в Telegram.

**Исправление:** обязательная проверка администратора; `payment_request_id`; сохранённое состояние `pending → approved/rejected`; атомарный переход и одно начисление на запрос.

### P1. Начисления подписки теряются при конкурентных операциях

Источник: [database.py:726–753](../../backend/database.py#L726).

Срок сначала читается, затем вычисляется и перезаписывается без транзакционной защиты всего действия. **Проверено:** параллельные начисления +7 и +30 дней дали +30 вместо +37.

**Исправление:** транзакция решения об оплате и начисления, уникальный ID начисления, журнал оснований изменений. Очередь SQL-операций aiosqlite не делает всю бизнес-операцию атомарной.

### P1. Чек может потеряться, хотя интерфейс сообщает об успехе

Источник: [api.py:443–480](../../backend/api.py#L443), [App.tsx:174–176](../../frontend/src/App.tsx#L174).

Заявка не сохраняется как отдельная сущность. Ошибка уведомления администратора перехватывается, после чего API возвращает `success`, а интерфейс очищает чек и обещает активацию.

**Проверено:** фиктивный сбой отправки администратору дал ответ `status=success`.

**Исправление:** сначала сохранять запрос и вложение, затем очередь уведомлений; возвращать реальный ID/состояние. Добавить ограничения размера/типа чека на сервере: ограничение UI недостаточно. У PDF-резюме отдельное серверное ограничение уже есть.

### P1. Доставка вакансий не учитывает бан и срок доступа

Источник: [database.py:659–674](../../backend/database.py#L659), [telethon_parser.py:180](../../backend/telethon_parser.py#L180), [api.py:522](../../backend/api.py#L522).

Выборка подписчиков проверяет канал и пользовательскую связь, но не бан и действительность подписки. **Проверено:** заблокированный и просроченный фиктивные пользователи вернулись как получатели. Аналогичные проверки нужны в действиях бота, включая перегенерацию.

**Исправление:** единая политика доступа, используемая API, ботом и обработкой вакансий.

### P1. Сообщения могут теряться или дублироваться

Источник: [telethon_parser.py:191–265](../../backend/telethon_parser.py#L191), [database.py:354](../../backend/database.py#L354), [787–812](../../backend/database.py#L787), [индекс без UNIQUE:224](../../backend/database.py#L224).

Последовательность: проверить дубликат → создать/закоммитить карточку → отправить Telegram. После сбоя отправки карточка уже существует, а повторная обработка отсекается как дубликат. Долговечной очереди доставки и автоматического повторения нет. Проверка дубликата и создание не атомарны, ограничение уникальности отсутствует.

**Проверено:** две конкурентные проверки пропустили один источник, после чего созданы две разные карточки одному пользователю. Отсутствие повторной доставки после ошибки подтверждено кодом; реальные Telegram-сбои в продакшне не воспроизводились.

**Исправление:** входные задания с ключом `(chat_id, message_id)`, уникальная карточка `(user_id, job_id)`, очередь `outbox` в той же транзакции. Сохранять число попыток, время следующей попытки, итог ошибки, Telegram message ID. Воркеры должны переживать рестарт без потери задания.

### P1. Вебхук открыт при отсутствии настройки защиты

Источник: [api.py:500–555](../../backend/api.py#L500), [config.py:28](../../backend/config.py#L28).

`/api/jobs/incoming` требует секрет только когда он задан. В локальном `.env` `JOBS_WEBHOOK_SECRET` не задан; проверенные Render-конфигурации тоже его не задают. Этот путь отличается от парсера: не применяет классификацию вакансии/генерацию отклика и не пишет его сквозную трассировку.

**Исправление:** закрыть endpoint по умолчанию, обязательная аутентификация интеграции и ограничение нагрузки; направить оба входа в общий сервис обработки. Фактическая конфигурация рабочего VPS не прочитана, поэтому состояние защиты именно там не подтверждено.

### P1. Авторизация допускает повтор старых данных; upstream использует HTTP

Источник: [auth.py:18,49](../../backend/auth.py#L18), [database.py:330–336](../../backend/database.py#L330), [api.py:181](../../backend/api.py#L181), [api.ts:129–145](../../frontend/src/api.ts#L129), [frontend/vercel.json](../../frontend/vercel.json), [vercel.json](../../vercel.json).

Проверка возраста `auth_date` существует, но реальные вызывающие функции не передают ограничение. Frontend отправляет сырые Telegram initData на каждом запросе. В конфигурации Vercel прокси направляет API-трафик по HTTP на VPS, включая авторизационные данные.

**Проверено изолированно:** подписанные фиктивным ключом initData с датой 2023 года приняты репозиторием; при явном ограничении возраста отклонены. Соответствие действующего деплоя локальной конфигурации не подтверждено.

**Исправление:** обязательный `auth_date` и ограничение возраста, короткая серверная сессия после обмена, HTTPS до бэкенда. При запуске production отклонять стандартный JWT secret/placeholder credentials, а не использовать предсказуемые значения по умолчанию. Локально JWT secret присутствует; его содержимое не публикуется.

### P1. Деплой способен перезаписать рабочие данные сервера

Источник: [deploy.py:20–21](../../scripts/deploy.py#L20), [121–141](../../scripts/deploy.py#L121), [175–185](../../scripts/deploy.py#L175).

Скрипт рекурсивно загружает весь checkout, не исключая `data/`, базы, их WAL/SHM, резервные копии и Telegram-сессию. Перезапуск происходит после загрузки. `.gitignore` этот SFTP-скрипт не защищает. Возвращаемые exit status удалённых команд не проверяются всеми вызывающими операциями, хотя в конце объявляется успех.

**Исправление:** allowlist исходных файлов, неизменяемый каталог релиза и отдельный каталог данных; явные миграции/backup, остановка при любой ошибке, контролируемое переключение релиза. Не запускать текущий скрипт как есть. Деплой в ходе аудита не выполнялся.

### P1. «Отправить отклик» не отправляет отклик заказчику

Источник: [bot_service.py:78–84](../../backend/bot_service.py#L78), [426–446](../../backend/bot_service.py#L426).

Кнопка меняет статус карточки на `APPLIED` и сообщает «отправлен», но отправки работодателю в обработчике нет. Это проверенный разрыв между обещанием интерфейса и действием приложения.

**Исправление:** определить продуктовый контракт: ручной отклик с честным названием/копированием текста или отдельная согласованная отправка с адресатом, состояниями, ограничениями и подтверждением результата.

### P2. Пользовательские каналы выбираются и распространяются неправильно

Источник: [database.py:632–649](../../backend/database.py#L632), [591–620](../../backend/database.py#L591), [318–324](../../backend/database.py#L318).

После `ON CONFLICT DO UPDATE` используется `cursor.lastrowid`, который может относиться к предыдущей вставке. **Проверено на реальном репозитории в изоляции:** существующий пользовательский канал ID 40 вернул ID 1 после вставки trace; ID 1 относится к другому каналу.

Все каналы профессии показываются с `COALESCE(is_enabled, 1)`, а startup включает их пользователям через seed/sync, включая пользовательские каналы. **Проверено:** другой пользователь увидел чужой пользовательский канал включённым без выбора; startup создал ему подписку на этот канал.

**Исправление:** `RETURNING id` или обязательный lookup по уникальному ключу; отделить общий рекомендованный каталог от источников конкретного пользователя; не менять пользовательский выбор при обычном открытии БД.

### P2. Запуск, остановка и диагностика здоровья не согласованы

Источник: [server.py:20–48](../../backend/server.py#L20), [app.py:48](../../app.py#L48), [telethon_parser.py:269–276](../../backend/telethon_parser.py#L269), [backend/render.yaml](../../backend/render.yaml).

Есть два разных entrypoint. `app.py` запускает daemon-thread при импорте и независимо показывает текст о работе 24/7. `server.py` запускает API, polling и parser рядом, но не имеет общей readiness-модели и полной процедуры отмены/закрытия всех ресурсов. `parser_stats.is_running` выставляется до успешного подключения и не сбрасывается. `backend/render.yaml` указывает `python app.py`, хотя такого файла внутри backend нет.

**Исправление:** единый composition root и контролируемый lifecycle; health/readiness по компонентам; отмена задач и закрытие всех БД/HTTP/Telethon ресурсов. Polling и parser должны быть singleton, иначе несколько реплик запустят обработку повторно. Добавить ограниченную конкурентность работы ИИ и backpressure.

### P2. Нет явного восстановления пропущенных входных сообщений

Источник: [telethon_parser.py:99](../../backend/telethon_parser.py#L99), [database.py:632](../../backend/database.py#L632).

Приём построен на новых событиях, без прикладного checkpoint и сверки истории после простоя. Добавление источника меняет SQLite, но не выполняет явное подключение/проверку доступа Telegram-аккаунта к каналу. Наличие пропущенных реальных сообщений не проверялось.

**Исправление:** состояния источника `pending/active/failed`, проверка доступа, checkpoint сообщения по каналу, восстановление после рестарта через общий идемпотентный обработчик.

## Логирование: покрытие по системам

**Ответ на вопрос «всё ли логируется»: нет.** Часть диагностики действительно работает, но полной сквозной наблюдаемости и подтверждённого производственного хранения/оповещения нет.

| Система | Что существует и проверено | Пробел |
|---|---|---|
| Telegram parser | INFO/WARNING/ERROR, trace_id, события SQLite: received, filters, matched, created, sent/failed/error; целевые тесты дали реальные записи | Нет checkpoint/retry; get_chat до защищённого try; ошибки обычно без traceback; статус running недостоверен |
| Бот | Logger `saas_bot`, команды `/debug`, `/trace`; тесты чтения trace и контроля админа этих диагностических команд прошли | Часть except молчит; нет единого журнала действий/изменений подписки; проверки admin payment handler отдельно недостаточны |
| ИИ/OpenRouter | WARNING при ошибке; проверен переход на шаблон | Нет общего trace_id, latency, model/result/fallback reason как структурированных полей; без ключа fallback не отмечается; карточка не сообщает, что ИИ не сработал |
| FastAPI | Обычно access/error logs Uvicorn; отдельные ошибки отправки чека логируются | Нет middleware request_id/status/duration и общего обработчика с traceback; `/incoming` проглатывает ошибки доставки и отвечает success; отсутствуют health/readiness |
| SQLite | Pipeline trace таблица; чтение/запись проверены | При очередной очистке хранится около 500 событий, не 500 вакансий; нет audit log бизнес-изменений и миграций; большинство ошибок операций не имеют собственного контекста |
| Frontend/Mini App | `console.error`, часть UI сообщает о сбое | Нет Error Boundary/центрального сбора ошибок/request_id; загрузка начальных данных подменяет ошибки null/[]; пользователь может видеть пустоту вместо ошибки |
| Процесс/сервер | В одном entrypoint basicConfig INFO; генерируемый systemd unit задаёт Restart=always | Нет подтверждённого внешнего монитора, alerting, retention/ротации; исправность journald/production-логов не проверена через SSH |
| Деплой | Печатает stdout/stderr и exit status команд | Нет сохранённого журнала релиза; exit status часто не влияет на успех операции; отсутствует проверка readiness после обновления |

Основания: [parser.py:89–96](../../backend/telethon_parser.py#L89), [matching_service.py:221–241](../../backend/matching_service.py#L221), [api.py:546–549](../../backend/api.py#L546), [database.py:1095–1127](../../backend/database.py#L1095), [App.tsx:257–261](../../frontend/src/App.tsx#L257).

Нужно связать `request_id / job_id / card_id / delivery_id / payment_request_id`; писать структурированные события с уровнем, компонентом, длительностью, исходом и безопасным контекстом. Для неожиданных ошибок сохранять traceback. Не писать Authorization, initData, полные ключи, чек/резюме целиком. Сохранять логи с ротацией/сроком хранения, метрики и оповещения о недоступности parser/ИИ, росте очереди и сбоях доставки. Префикс токена в текущей диагностике заменить на bot ID/username: фрагменты секрета для идентификации не нужны.

## Предлагаемая архитектура после адресного рефакторинга

Сохранить один репозиторий и модульный монолит. Организовать следующие границы:

1. `domain`: политика доступа, состояния вакансии/карточки/доставки/платежа, правила переходов.
2. `application`: общая обработка вакансии, создание карточек, генерация отклика, решение об оплате. API и Telegram handlers только адаптируют вход/выход.
3. `storage`: репозитории, явная транзакция/unit of work, версия схемы и миграции, уникальные ключи. Runtime data и backups отдельно от исходников.
4. `adapters`: Telegram Bot API, Telethon, OpenRouter; таймауты и классификация ошибок.
5. `workers`: долговечные входные задания и outbox, ограничение параллелизма, retry/backoff, восстановление после остановки. Перед повтором учитывать возможный неопределённый исход внешней отправки — одна outbox не гарантирует exactly-once в Telegram.
6. `runtime`: единый запуск, singleton workers, readiness, graceful shutdown, безопасный деплой и общая наблюдаемость.

Не нужны микросервисы, Kafka или полный перенос UI ради исправления этих ошибок. На первом этапе очередь/outbox может храниться в той же БД; брокер добавлять по измеренной потребности.
